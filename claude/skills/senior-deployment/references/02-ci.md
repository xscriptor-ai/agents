# CI

Scope: pipeline design and structure, GitHub Actions patterns, caching, matrix builds, required checks, artifact signing, and pipeline security with OIDC and least privilege.

## Pipeline Design

A pipeline is a production system. It has an owner, an SLO for duration and reliability, and an error budget.

Principles:

- Fast feedback first: lint, format, type-check, and unit tests run in the first minutes. Slow suites run in parallel or after.
- Fail fast, but only on signal. Blocking on a flaky test trains people to rerun rather than read.
- Deterministic: same commit plus same inputs produces the same result. Pin tool versions and container images.
- Idempotent: re-running a job neither duplicates side effects nor corrupts state.
- Cached, not stale: caches are keyed on lockfiles and tool versions, with restore keys as a fallback.
- Observable: duration, queue time, failure rate, and flake rate are tracked per job. See `./07-observability-rollback.md`.
- Hermetic where possible: no implicit network dependency on a developer's machine or a mutable external service.

Canonical stage order:

| Stage | Purpose | Gate |
|---|---|---|
| Static analysis | Format, lint, types, dependency policy | Blocking |
| Unit tests | Fast, isolated, parallelized by shard | Blocking |
| Build | Produce artifact once, sign, attest, SBOM | Blocking |
| Integration tests | Real dependencies via containers or ephemeral infra | Blocking |
| Security scans | SAST, dependency CVEs, secret scan, IaC policy | Blocking with documented exceptions |
| Publish | Push image and versioned packages to registry | Blocking |
| Deploy staging | Automated promotion of the same digest | Automatic |
| Verify staging | Smoke, contract, migration checks | Automatic |
| Deploy production | Progressive delivery per `./03-cd-strategies.md` | Policy-driven |
| Post-deploy | Release markers, SLO watch, auto-rollback | Automatic |

- Build artifacts exactly once. Everything downstream consumes the same digest. See `./01-containers.md`.
- Keep deploy jobs thin: they should apply a known artifact, not compile code. Rollback then has no build step to fail.
- Separate orchestration from execution: a small number of reusable entry workflows call versioned reusable pipelines per service.

## GitHub Actions Patterns

### Workflow Structure

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@<full-sha> # pinned
        with: { persist-credentials: false }
      - uses: actions/setup-node@<full-sha>
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci
      - run: npm test
```

Rules:

- Pin third-party actions to a full commit SHA, not a tag. Dependabot or Renovate can bump SHAs; tags can be retargeted.
- Set `permissions` explicitly at workflow or job level. Default to `contents: read`; add only what a job needs.
- Use `concurrency` with `cancel-in-progress` on PRs to eliminate redundant runs.
- Use `timeout-minutes` on every job; a hung job holds a runner and a queue slot.
- `persist-credentials: false` on checkout unless the job pushes back.
- Prefer `pull_request` over `pull_request_target`. If you need `pull_request_target`, never run untrusted code with a write token or secrets.
- Reusable workflows (`workflow_call`) for shared pipelines; composite actions for shared step sequences. Version reusable workflows with a tag or SHA like any dependency.
- Use environments with protection rules for production deploys; required reviewers are a control, not a substitute for automated gates.
- Self-hosted runners are production infrastructure: isolate untrusted jobs, patch them, and never give them static cloud credentials.

### Caching

| Cache | Key | Notes |
|---|---|---|
| Package manager | Lockfile hash plus OS and runtime version | Provider `setup-*` caches are usually best |
| Compiled output | Source tree hash, tool version | Only safe when determinism is proven |
| Container layers | Base digest plus lockfile | Registry-backed BuildKit cache |
| Test results | Test file set plus commit range | Enables selective reruns |
| Tool binaries | Version manifest hash | Avoids re-downloading CLIs every run |

- Scope caches: PR caches should not be writable from forks. Never cache credentials or `.env` files.
- Treat cache as an optimization only; a cold run must still pass. Flaky failures that vanish on cache hit usually mean undeclared inputs.
- Rotate caches when changing compilers or package managers, or restore stale artifacts.

### Matrix Builds

- Use matrices for OS, runtime-version, and shard combinations; keep the full matrix meaningful, not decorative.
- `fail-fast: false` when you need the complete failure picture; `fail-fast: true` when a red leg makes the rest pointless.
- Keep matrix length bounded; a 40-leg matrix costs more than it informs. Use `include`/`exclude` to encode exceptions explicitly.
- Shard tests by file count or historical duration; unbalanced shards negate the parallelism.
- Aggregate results in a single required check so branch protection does not require knowing the matrix shape.

### Required Checks and Merge Flow

- Branch protection requires the aggregate gate, not individual jobs, so adding a job does not break merges.
- Enable merge queue for busy repositories; it tests the actual merge result rather than the PR head.
- Required checks must be hermetic and reasonably fast (a target under ten minutes is healthy; verify expectations with the team).
- A required check that is skipped for some PRs (docs-only) should still report success explicitly, or protection will hang.
- Protect the workflow files themselves with CODEOWNERS; a PR that edits its own gate needs review.

## Pipeline Security

Pipeline credentials are production credentials.

- Use OIDC federation to cloud providers and registries; delete long-lived access keys from CI. Bind the trust policy tightly: repository, ref or environment, and workflow.
- Scope tokens to the job and the environment: a test job must not assume the production deploy role.
- Never print secrets; mask values and review logs for accidental echoes. `set -x` in a job with secrets is an incident waiting for a trigger.
- Treat all PR input as hostile: branch names, commit messages, file contents. Avoid interpolating `${{ github.event.* }}` directly into `run:` blocks; pass through `env:` and quote.
- Pin dependencies of the pipeline itself (actions, container images, CLIs) by digest or SHA.
- Sign artifacts and attest provenance in CI, and verify in deployment. See `./01-containers.md` and `./09-release-management.md`.
- Use ephemeral runners where feasible; persistent runners accumulate state and credentials.
- Audit who can edit workflows, and log secret access and OIDC token issuance.

```yaml
jobs:
  deploy:
    permissions:
      id-token: write
      contents: read
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@<full-sha>
        with:
          role-to-assume: arn:aws:iam::<account>:role/ci-deploy
          aws-region: <region>
```

## Test Selection

- Run everything on `main` and on merge queue candidates.
- On PRs, select affected tests by changed paths in a monorepo. Selection must fail open: if the tooling cannot determine impact, run the full set. See `../../monorepo/SKILL.md` if the monorepo pack is installed.
- Track flake rate per test; quarantine with an owner and expiry, never silently retry forever.
- Upload test reports and coverage as artifacts; downstream tools should not re-run tests to render results.

## Pipeline Observability

- Emit deploy events and build IDs into telemetry so a release can be traced from commit to production. See `./07-observability-rollback.md`.
- Dashboard queue time, duration, success rate, and cost per pipeline.
- Alert on sustained failure of the default-branch pipeline: a broken main blocks everyone.
- Record who or what triggered a deploy (actor, workflow run, event) for audit. See `./09-release-management.md`.

## Anti-Patterns

- Secrets stored as repository or organization variables when OIDC is available.
- `permissions: write-all` or leaving default broad permissions.
- Unpinned `@main` actions in a workflow with deploy privileges.
- Long-lived service-account JSON keys in CI secrets.
- Rebuilding the artifact in the deploy job.
- Retrying failed jobs automatically to hide flakes.
- Matrix explosion for combinations nobody supports.
- Running privileged PR code on self-hosted runners with cloud access.
- Required checks that only run on some paths without explicit success reporting.
- Caches holding credentials or written by untrusted forks.

## Checklist

- [ ] One artifact built once, signed, attested, and promoted by digest.
- [ ] Fast static and unit stage; slow suites parallelized or deferred.
- [ ] Actions pinned by SHA; `permissions` minimal per job.
- [ ] Concurrency and timeouts set on every workflow.
- [ ] Caches keyed correctly and never hold secrets.
- [ ] Matrix bounded, sharded, and aggregated into one required check.
- [ ] OIDC used for cloud and registry access; trust policy scoped to repo/ref/environment.
- [ ] Deploy jobs thin, environment-protected, and auditable.
- [ ] Flake tracking and quarantine process in place.
- [ ] Pipeline duration, failure, and cost visible on a dashboard.
