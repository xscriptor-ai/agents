# End-to-End Testing

Selecting user-critical journeys, writing maintainable Playwright suites, managing auth and test data, capturing artifacts, and controlling flake.

## What E2E Is For

An E2E test drives the system through its real user-facing entry point (browser, mobile
app, CLI) against a deployed or locally composed environment. Its unique value is proving
that the whole chain works together: frontend build, API, auth, database, third parties,
and configuration.

E2E is the most expensive and most brittle layer. Its scope should be **journeys**, not
pages or endpoints:

- Sign up, verify email, first login.
- Checkout with a saved payment method.
- Password reset and session expiry.
- Permission boundary: the action a user must not be able to do.
- Deployment smoke: app loads, health endpoint green, login works.

If a journey can be verified by an API-level or component test, do that instead
([01-strategy](./01-strategy.md)).

## Critical-Path Selection

Score journeys by revenue, safety, and frequency. Select 5-15 for the main suite; more for
regulated products, fewer for early-stage ones.

| Candidate | Keep as E2E | Better layer |
|---|---|---|
| Login (happy path + failure) | Yes | - |
| Payment/checkout | Yes | - |
| Signup with email verification | Yes | - |
| Authorization denial | Yes | - |
| Form field validation | No | Component |
| Pagination/sorting | No | Integration/component |
| API schema correctness | No | Contract ([06-contract](./06-contract.md)) |
| Every settings toggle | No | Component + one E2E smoke |
| Mobile/responsive variants | One per breakpoint | Visual regression |

Rules:

- One journey per test; no "mega journeys" that chain ten features.
- Tag tests (`@smoke`, `@critical`, `@nightly`) so pipelines can select subsets.
- A failed critical journey must name the user-visible capability, not the selector.
- Re-evaluate quarterly: delete E2E tests that have not caught a bug in a year or that
  duplicate lower-layer coverage.

## Playwright Patterns

```ts
import { test, expect } from "@playwright/test";

test("checkout with saved card", async ({ page }) => {
  await page.goto("/cart");
  await page.getByRole("button", { name: "Checkout" }).click();
  await page.getByLabel("Card ending in 4242").click();
  await page.getByRole("button", { name: "Pay now" }).click();
  await expect(page.getByRole("heading", { name: "Order confirmed" })).toBeVisible();
  await expect(page.getByTestId("order-total")).toHaveText(/\$\d+\.\d{2}/);
});
```

- Prefer **role and label selectors** (`getByRole`, `getByLabel`, `getByText`) — they track
  accessibility and survive refactors.
- `data-testid` for elements without a stable accessible name. Name test IDs by domain
  concept, not by layout.
- Never use CSS chains tied to implementation (`div > .MuiBox-root:nth-child(3)`) or XPath.
- Assert on user-visible outcomes (heading, URL, toast, network response) — not on
  internal component state.
- Use auto-waiting assertions (`toBeVisible`, `toHaveText`) instead of explicit sleeps.
- Keep helpers thin: page objects are fine for repeated flows, but over-abstracted page
  objects hide the user story.
- Use `test.step` for readable traces on long journeys.
- Parallelism is per-file by default; make tests independent so this stays safe.

### Playwright project layout

```text
e2e/
  playwright.config.ts
  fixtures/
    auth.ts            # storageState setup
    data.ts            # unique data builders
  tests/
    checkout.spec.ts
    auth.spec.ts
  .auth/               # gitignored storage states
```

## Selectors: Priority Order

| Priority | Locator | Notes |
|---|---|---|
| 1 | `getByRole` | Best proxy for user intent; enforces a11y |
| 2 | `getByLabel` / `getByPlaceholder` | Form fields |
| 3 | `getByText` | Visible copy; keep assertions tolerant of case/wrapping |
| 4 | `getByTestId` | Explicit contract with tests; stable |
| 5 | CSS attributes (`[name=email]`) | Acceptable when semantic |
| 6 | CSS structure, XPath, nth-child | Forbidden; refactor-brittle |

If an element has no queryable role or label, that is often an accessibility defect worth
fixing in the app itself.

## Authentication State

Authenticating through the UI in every test multiplies runtime and flake. Use storage
state or API login:

```ts
// global setup: log in once, save storage state
import { test as setup, expect } from "@playwright/test";

setup("authenticate", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("Email").fill(process.env.E2E_USER!);
  await page.getByLabel("Password").fill(process.env.E2E_PASS!);
  await page.getByRole("button", { name: "Sign in" }).click();
  await expect(page).toHaveURL(/\/dashboard/);
  await page.context().storageState({ path: ".auth/user.json" });
});
```

- Keep one authenticated context per role, not per test. For role-based tests, save
  separate storage states.
- Test the login journey itself in a dedicated spec, unauthenticated.
- Verify session expiry/login-required behavior in at least one negative test.
- Never store real user credentials; create ephemeral users via API in global setup
  ([07-test-data](./07-test-data.md)).
- Storage state contains tokens — gitignore it and treat CI artifacts accordingly.

## Test Data for E2E

- Generate unique data per run (timestamp/UUID suffix) so parallel runs and retries do not
  collide.
- Prefer API-based setup (seed via endpoints or direct DB) over clicking through ten pages;
  keep only the flow under test in the UI.
- Delete or expire created data when the environment is shared; tag rows with a run ID for
  bulk cleanup.
- Use dedicated sandbox/test accounts for third parties (payments, email, SMS). Never
  point E2E at production services.
- For email/SMS verification, use catch-all mailboxes or provider sandboxes with polling
  helpers; do not assert on external delivery.
- Keep a documented test-user matrix for roles and entitlements.

## Artifacts: Trace, Video, Screenshot

Configure artifacts to fire on failure, not on every passing test:

```ts
// playwright.config.ts
export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: {
    trace: "on-first-retry",
    video: "retain-on-failure",
    screenshot: "only-on-failure",
    baseURL: process.env.E2E_BASE_URL ?? "http://localhost:3000",
  },
  reporter: [["html", { open: "never" }], ["junit", { outputFile: "results.xml" }]],
});
```

- **Trace is the primary debugging tool.** `npx playwright show-trace trace.zip` replays
  DOM, network, console, and screenshots.
- Upload artifacts to CI for failures only; retention windows keep storage bounded.
- Add timestamps and run IDs to artifact names when artifacts are aggregated.
- On flake, read the trace before rerunning. Retrying without reading the trace discards
  the only evidence ([08-flaky-ci](./08-flaky-ci.md)).

## Flake Control in Browser Tests

| Symptom | Likely cause | Fix |
|---|---|---|
| Passes locally, fails in CI | Animations/CPU speed, fonts | Disable animations, increase assertion timeout, pin viewport |
| Passes alone, fails in suite | Shared user/data, storage state races | Unique data per test, independent contexts |
| Intermittent "element not visible" | Explicit sleep or missing wait | Auto-waiting locator assertions |
| Failed on retry only | Real race or external dependency | Diagnose from trace; do not keep retrying |
| Time-based assertions | Locale/timezone differences | Pin `timezoneId`, `locale`, freeze test clock |
| Network flake | Third-party sandbox hiccups | Stub non-critical third parties; retry only at boundary |
| Hover/animation flake | Moving targets | `page.mouse.move` sequences or disable motion |

Determinism levers:

```ts
use: {
  viewport: { width: 1280, height: 720 },
  deviceScaleFactor: 1,
  timezoneId: "UTC",
  locale: "en-US",
  colorScheme: "light",
  reducedMotion: "reduce",
},
```

- Seed random data from a per-test seed recorded in the report.
- Block or stub non-essential third parties (analytics, chat widgets, ads) to cut noise.
- Prefer one browser (Chromium) in the PR gate; run WebKit and Firefox nightly or before
  release.
- Budget: fail the build if the suite's flake rate exceeds the threshold, not just if tests
  fail ([09-coverage-metrics](./09-coverage-metrics.md)).

## Environment Strategy

| Environment | Purpose | Data |
|---|---|---|
| Local compose (app + DB + stubs) | Developer inner loop | Ephemeral, generated |
| CI ephemeral | PR gate | Ephemeral per run, containers |
| Shared staging | Nightly E2E, integration | Reset or namespaced per run |
| Production | Synthetic monitoring only | Read-only journeys or dedicated tenant |

- Prefer ephemeral environments for PRs: no shared state, no queueing behind other teams.
- If staging is shared, namespace all data by run ID and enforce cleanup TTLs.
- Production synthetic tests use dedicated accounts and read paths; never mutate real
  customer data.
- Keep environment configuration explicit and versioned; no hand-edited staging state.

## Anti-Patterns

- E2E for everything; suites of hundreds of browser tests in the PR gate.
- Sleep-based waits; `waitForTimeout(5000)` as a fix.
- Selectors on CSS classes or DOM structure.
- UI login in every test.
- Asserting on exact pixel positions or unmasked timestamps.
- Running against production data or real payment credentials.
- Retries set to 3+ with no flake tracking; the suite becomes a noise generator.
- Copy-pasted journeys that differ only in test data; parameterize.
- No artifact retention: failures cannot be diagnosed after the runner is gone.

## E2E Checklist

- [ ] 5-15 critical journeys selected by risk, not by page count.
- [ ] Role/label selectors dominate; no structural CSS or XPath.
- [ ] Auth via storage state or API; login journey tested separately.
- [ ] Test data unique per run; cleanup owned and automated.
- [ ] Trace/video/screenshot on failure, uploaded with retention.
- [ ] Deterministic viewport, timezone, locale, and motion settings.
- [ ] Flake rate measured and gated; quarantine with owner and expiry.
- [ ] Ephemeral or namespaced environments; no production data.
- [ ] Browser matrix: Chromium per PR, cross-browser nightly/release.
