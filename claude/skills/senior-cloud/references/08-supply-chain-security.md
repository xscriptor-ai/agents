# Supply-Chain Security

> Scope: securing the path from source to running workload — provenance, signing, SBOMs, scanning, admission verification, hardening, and secrets.

## Threat model

| Stage | Threats | Primary controls |
|---|---|---|
| Source | Compromised developer account, malicious dependency, typo-squatting | SSO+MFA, branch protection, dependency review, lockfiles |
| Build | Poisoned CI, tampered build steps, credential theft | Ephemeral runners, OIDC, isolated builds, provenance |
| Artifact | Registry tampering, tag mutation, unsigned images | Digests, signing, registry immutability |
| Deploy | Unauthorized images, policy bypass, secret exposure | Admission verification, least privilege, workload identity |
| Runtime | Vulnerable dependency exploitation, lateral movement | Scanning, patching cadence, network policy, hardening |

The goal is not zero vulnerabilities; it is that every deployed artifact can be traced to a reviewed source commit and a trusted build.

## SLSA and provenance

SLSA (Supply-chain Levels for Software Artifacts) provides a common vocabulary. Use the tracks/levels model current in 2026 rather than memorized level numbers; verify the spec upstream.

Practical progression:

1. **Build L1-L2**: builds run in CI with a documented, versioned build definition; provenance is generated and available.
2. **Build L3**: hardened, ephemeral build environment; provenance is non-forgeable by the build itself and signed.
3. **Distribute**: artifacts are signed and consumers verify before deploy.

What to implement first, in order:

- One build definition in Git per artifact; the pipeline is code.
- Provenance generated by the CI platform or a dedicated builder (for example in-toto attestations), signed, and stored alongside the artifact.
- Digest-addressed artifacts; registries with immutability enabled so a tag cannot be re-pointed.
- Verification in admission and, where possible, at runtime.

## Sigstore and cosign

- **cosign** signs and verifies OCI artifacts, blobs, and attestations. Keyless signing uses your CI's OIDC identity and Fulcio; Rekor provides a transparency log.
- Key-based signing still works (KMS keys) where keyless is not permitted; KMS-backed keys beat file-based keys and passphrases.
- Sign the digest, then attach SBOM and provenance attestations to the same digest.
- Verification policy must bind identity: `--certificate-identity` and `--certificate-oidc-issuer` for keyless, or the public key for key-based. Verifying a signature without checking who signed it is security theater.
- Store signatures as OCI artifacts in the registry (`.sig`, `.att` tags) so verification does not need outbound access at admission time; mirror the transparency log entries you depend on.

```bash
# Sign an image in CI (keyless; uses the workflow OIDC identity)
cosign sign --yes ghcr.io/example/api@sha256:REPLACE_DIGEST

# Verify with identity binding
cosign verify ghcr.io/example/api@sha256:REPLACE_DIGEST \
  --certificate-identity "https://github.com/example/api/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

# Attach an SBOM attestation
cosign attest --yes --predicate sbom.spdx.json --type spdxjson ghcr.io/example/api@sha256:REPLACE_DIGEST
```

## SBOM

- Generate an SBOM per artifact at build time: SPDX or CycloneDX, in a machine-readable form, stored and signed with the artifact.
- Generation tools (syft, Trivy, buildkit plugins, or CI-native generators) should enumerate OS packages, language dependencies, and licenses.
- Use the SBOM for: vulnerability scanning of shipped components, license compliance, incident response ("are we affected by CVE-X?"), and customer questionnaires.
- Keep SBOMs per digest, not per release name; rebuilds produce new SBOMs.
- VEX (Vulnerability Exploitability eXchange) lets you state "not affected" with reasoning; publish VEX for accepted risks so scanners and customers stop re-reporting them.
- SBOM quality varies; validate that the generator includes transitive dependencies and package versions, or the document is compliance theater.

## Vulnerability scanning and gates

| Scope | Tools | Cadence |
|---|---|---|
| Dependencies (SCA) | Dependabot/Renovate, Trivy, Grype, OSV scanners | Every PR and nightly |
| Container image | Trivy, Grype, cloud registry scanning | On build and continuously on running digests |
| IaC and manifests | Trivy config, Checkov, kube-linter | Every PR |
| Runtime | Admission-blocking of new criticals, runtime security agent | Continuous |
| Secrets | gitleaks, trufflehog, provider secret scanning | Pre-commit, PR, continuous |

Gate design:

- Block on critical/high with a known fix; time-box exceptions with owner and expiry.
- Do not block on unfixable base-image noise; instead track base image age and rebuild cadence.
- Separate the "can we ship?" gate (build-time, priority-based) from the "what is running?" report (continuous).
- Rebuild and redeploy when base images or dependencies receive fixes; scanning without a rebuild path changes nothing.

## Admission verification

Verify signatures and attestations before the pod is admitted:

- **Kyverno `verifyImages`**: checks signatures, keys/identities, and attestations; can also mutate the image to its digest.
- **Sigstore policy-controller**: ClusterImagePolicy with keyless identity rules and attestation checks.
- **Ratify**: verification with external policy engines and multiple verifiers.
- Admission webhooks themselves must be highly available; a failing verification policy should fail closed for security but you must operate it with redundancy and scoped rules.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-images }
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match:
        any:
          - resources: { kinds: ["Pod"] }
      verifyImages:
        - imageReferences: ["ghcr.io/example/*"]
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/example/*"
                    issuer: "https://token.actions.githubusercontent.com"
```

Pair admission policy with runtime policy: image verification at admission plus continuous scanning of running images catches drift and registry-side changes.

## Workload hardening

- Base images: distroless or minimal (scratch, alpine-style) with only needed packages; pin by digest. Rebuild regularly to pick up patched bases.
- Run as non-root with a fixed high UID; read-only root filesystem; drop all capabilities; `allowPrivilegeEscalation: false`; `seccompProfile: RuntimeDefault`.
- Pod Security Admission at `restricted` for namespace defaults; exceptions are per-workload and documented. See `./01-kubernetes.md`.
- Disable service account token automounting unless needed; use projected tokens with audience and expiry.
- No `hostPath`, `hostNetwork`, or privileged containers without a documented, reviewed exception.
- Keep an SBOM-linked runtime inventory so "which workloads run log4j?" is a query, not an investigation.

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
USER 65532:65532
ENTRYPOINT ["/api"]
```

## Secrets management

- Source of truth: a secret manager (Vault, cloud secret manager) or encrypted Git (SOPS) with a documented decision. See `./02-gitops.md` for GitOps patterns.
- Delivery into workloads: External Secrets Operator or Secrets Store CSI; avoid secrets in plain Kubernetes Secrets created by hand.
- Identity: workloads authenticate to the secret store with workload identity, not static tokens.
- No secrets in environment variables where avoidable (they leak through `kubectl describe`, crash dumps, and child processes); prefer files with tight permissions or in-memory fetch via SDK.
- Rotation: automated, short-lived where possible (database IAM auth, OIDC tokens), scheduled otherwise. Test rotation in staging; a rotation procedure that has never run is broken.
- CI: OIDC to cloud roles, no repository secrets for cloud credentials; mask anything that might appear in logs and rotate what leaks.

## Anti-patterns

- Signing images but not binding an identity in verification.
- Scanning only at build time and never rebuilding so fixes never reach production.
- Deploying mutable tags while claiming digest immutability.
- One shared signing key across all repositories, stored as a CI secret.
- Admission policy with a verification webhook on all resources and no high availability.
- Ignoring base image age; "we scan" while running a two-year-old base.
- Secrets duplicated into Kubernetes Secrets and never rotated.
- SBOMs generated but never used in an actual incident or customer response.

## Checklist

- [ ] Build pipeline defined in Git with ephemeral runners and OIDC.
- [ ] Provenance generated and signed for every artifact.
- [ ] Artifacts signed (keyless or KMS) with identity-bound verification.
- [ ] Registry immutability enabled; deploys reference digests.
- [ ] SBOM produced, stored, and signed per digest; VEX for accepted risks.
- [ ] Scanning gates on PR, build, and running workloads; rebuild cadence defined.
- [ ] Admission verification enforced with HA webhooks and scoped rules.
- [ ] Hardening baseline applied cluster-wide with documented exceptions.
- [ ] Secrets from a central store with workload identity and tested rotation.
- [ ] Incident query "which workloads contain component X" answerable in minutes.
